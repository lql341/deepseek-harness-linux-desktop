# ADR-0003：分阶段回移 Linux 原生文件拖拽

- 状态：`proposed`
- 日期：2026-11-01
- 负责人：Linux Desktop 维护者
- 适用范围：`apps/desktop`、`apps/desktop-host`、`packages/util/file-drag`、`packages/client/ui-file-drag`、打包与验收

## 决策

分四个阶段回移原生文件拖拽，并在第 0 阶段证明目标会话可用之后再决定是否保留拖拽手势。第 0 阶段是原型验证而不是移植：Electron 的 `webContents.startDrag` 在 Wayland 上支持有限，而一个静默无反应的手势比有文档说明的“保存到下载目录”更糟。

如果验证显示 `startDrag` 在 X11 可用、在 Wayland 可用或有诚实的降级方案，就继续移植。如果 Wayland 无法拖拽，先交付不带拖拽的导出路径，把拖拽手势作为仅 X11 的能力，并在界面上明确标注。

## 背景

固定基线 `dsh-v0.2.1-rc.5` 没有原生文件拖拽。上游 `dsh-v0.2.2-alpha.2` 在四个区域加入该能力：

| 区域 | 开发线文件 | 行数 |
| --- | --- | --- |
| 共享命名与请求类型 | `packages/util/file-drag`（`src/index.ts`、`tests/names.spec.ts`、包元数据） | 约 110 |
| Desktop 原生准备 | `apps/desktop/src/file-drag.ts`、`apps/desktop/src/file-drag-files.ts` | 约 290 |
| Host 资源授权 | `apps/desktop-host/src/file-drag.ts` | 约 120 |
| 客户端插件与反馈 | `packages/client/ui-file-drag`（客户端入口、语言、测试） | 约 600 |

桌面侧依赖共享的 Host 与客户端 API（`util-file-drag` 类型、Host 资源地址约定、可信窗口 IPC、临时文件生命周期）。只复制桌面侧会留下死代码，这也是当初选择推迟而不是部分应用的原因。

调用点也要改：交付物文件操作和工作区文件列表决定什么可以被拖拽，客户端在 Host 无法授权借用资源时必须回退到字节复制。

## 第 0 阶段：可行性验证（必须先做）

在固定基线上构建一个最小 Electron 窗口，挂上调用 `webContents.startDrag` 的 `dragstart` 处理，尝试把文件拖到文件管理器：

| 会话 | 记录内容 |
| --- | --- |
| X11（Openbox 或 GNOME on Xorg） | 放下后是否产生文件、接收方看到的 MIME 类型、临时文件存活时间是否足够 |
| Wayland（GNOME 或 KDE） | 同样观察，加上 `startDrag` 是抛错、无操作，还是通过 `xdg-desktop-portal` 生效 |
| 两者 | `app.getPath('temp')` 是否可用于暂存副本，拖拽取消后是否泄漏文件 |

出口条件：每个会话都有记录的“可用/不可用”。Wayland 不可用不阻塞该功能，但会改变验收范围和界面文案。

## 阶段

| 阶段 | 交付物 | 出口条件 |
| --- | --- | --- |
| 0 | 验证结果记录在本 ADR | 每个会话都有可用/不可用记录和降级决策 |
| 1 | `packages/util/file-drag` 加 Desktop 原生路径，并接入一个调用点（把交付物拖出） | 文件以正确文件名和类型落到目标；临时文件在有界宽限期后清理；非受信渲染进程无法请求拖拽 |
| 2 | 用 Host 资源借用替代字节复制 | Host 按地址授权资源，主进程校验大小与摘要，授权不可用时调用方回退到字节 |
| 3 | `packages/client/ui-file-drag` 反馈与本地化 | 被拒绝或失败的拖拽显示本地化反馈；成功拖拽不显示 |

每个阶段都是独立补丁、独立验证运行。只增加代码而没有可达调用方的阶段在评审中会被拒绝，因为产品使用策略要求每个维护中的包都有实际消费者。

## 影响

- 移植会引入基线没有的工作区依赖（`mime`），因此锁文件会变化。该包很小且已作为传递依赖存在，但锁文件差异仍需单独评审。
- 原生拖拽是特权操作：主进程会把用户文件写到磁盘并把路径交给操作系统。它只能接受受信渲染进程的请求，并要清洗文件名、限制大小并清理。
- Wayland 支持是产品问题而非代码问题。合成器无法交付时，移植版不得宣称支持拖拽。
- 该能力增加了每次上游迁移都要重新验证的面，尤其是共享的 `util-file-drag` 类型。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 四个区域一次性复制 | 1100 行跨包改动无法评审或二分定位；任一失败会阻塞其他所有修复 |
| 只复制共享命名工具 | 没有消费者，产品使用策略会拒绝，用户可见功能也不存在 |
| 只提供“保存到下载目录” | 最简单且处处可用，但失去了用户预期的交互；保留作为降级方案 |
| 等待更新的上游版本 | 开发线是 alpha；把整个移植 rebase 到它的风险大于分阶段回移 |

## 风险

- `startDrag` 在 Wayland 可能不可用，使该手势成为 X11 专属。缓解：第 0 阶段在任何移植工作之前决定。
- 如果放置目标始终不读取，临时文件可能在应用退出后残留。缓解：采用开发线的有界读取宽限期，并在下次启动时清理。
- 渲染进程被攻破可能请求任意文件。缓解：主进程从不接受渲染进程传来的路径，只接受字节或 Host 已授权的地址。
- 锁文件变化可能扰动无关依赖解析。缓解：只新增一个依赖并单独评审。
