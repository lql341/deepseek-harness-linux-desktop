# ADR-0002：以可选用附加组件的方式发布 dsh-superagent 原型

- 状态：`proposed`
- 日期：2026-11-01
- 负责人：Linux Desktop 维护者
- 适用范围：Linux Desktop 打包、profile 组合、插件管理、发布与支持

## 决策

不把 `dsh-superagent` 作为默认桌面功能。以可选附加组件的形式发布；在该打包方式实现之前，先记录受支持的手动安装方式。

该原型是一个 DSH Bundle，把单个 GitHub 仓库变成主动型 agent 服务。它需要独立的 DSH profile、独立的后台进程、专用的 GitHub 账户，以及可选的飞书机器人。这些要求与默认开启的桌面 bundle 不兼容，因为桌面必须服务于从不配置 GitHub、也不运行服务的人。

推荐顺序是：

1. 记录手动 `dsh plugin` 安装方式，以及当前原型需要的兼容性修补。
2. 在 Linux 包中加入离线、非默认的附加组件：构建产物、把它安装到独立 `superagent` profile 的设置动作，以及成文的服务生命周期。
3. 只有上游采纳原型并提供元数据、语言、图标和兼容性责任人后，才提升为桌面 profile 内的一等可选 bundle。

## 背景

### 原型是什么

`dsh-superagent` 监听 GitHub，并可选监听飞书。被允许的请求会变成工作项；bundle 在自己的 agent 会话和目录中执行，并在原会话中回复，例如给出一个 pull request。Web 面板显示需要人处理的事项。仓库自述为研究原型而非官方产品，其工程实践可能与 Harness 核心不同。

它的包声明了 `dsh.bundle.patch`、Web 客户端插件、worker 与 router preset，以及 Harness 包的 peer 依赖。它没有发布到公共 registry，因此离线包必须携带 tarball 或 vendored 构建产物。

### 运行时需要什么

| 需求 | 为什么需要 | Linux deb 是否提供 |
| --- | --- | --- |
| 独立 DSH profile | 插件会改变进程级 `PATH` 和 git 设置，并且需要独立重启 | 否；Desktop 只拥有一个 profile |
| 独立 `superagent` profile 与服务 | 桌面窗口关闭后服务仍需运行 | 否；没有随包服务单元或启动器 |
| 以 agent 账户登录的 `gh` | 读取通知、推分支、开 pull request | 否；不是包依赖 |
| `lark-cli` 与飞书机器人 | 可选的聊天来源 | 否 |
| `tmux` 与 `python3` | 随附的 start、stop、status 脚本使用两者 | Python 不保证存在；tmux 未安装 |
| git worktree 与本地 clone | 每个 ticket 一个工作目录 | `git` 存在，但没有准备 clone |
| 模型 provider 与凭据 | 每个执行器会话都需要模型 | 由使用者配置，不随包提供 |
| 可写 state 目录 | 数据库、锁、命令 shim 和 work tree | 否；必须留在包外 |

原型文档还建议使用独立操作系统账户，因为两个 preset 都以桌面用户身份完整权限运行，worker 可以读取操作者主目录。桌面附加组件必须说明这一边界，而不是隐藏它。

### 兼容性证据

原型的公开 peer 和 devDependencies 固定在 `0.2.1-alpha.2`。Linux 基线固定为 `dsh-v0.2.1-rc.5`，所有 peer 都有已发布版本。

一次本地实验把所有 `@deepseek-ai/dsh-*` 固定版本改为 `0.2.1-rc.5`，把 `@deepseek-ai/schemastery` 改为 `~3.18.5`，删除锁文件安装后运行包检查：

| 检查 | 针对固定基线的结果 |
| --- | --- |
| 依赖解析 | 所有 Harness peer 解析到 `0.2.1-rc.5`；声明的 engine 范围满足 |
| 单元测试 | 59 个文件、1197 项测试通过 |
| Bundle 构建 | `tsdown` 产出服务端、watch、客户端和类型产物 |
| 类型检查 | 因两处 API 漂移在三个文件报四个错误 |

两处漂移都很小且已知：

- 原型基线之后 `ConfigFormSnapshot.mode` 被移除。部署面板及其 fixture 仍在读取 `mode === 'memory'`。
- `webServer.port` 在监听绑定前现在是可选的，直接把该值传给路由处理器的代码不再通过类型检查。

两处漂移都不改变行为，修补只需几行。它们说明原型接近固定基线但并非直接可用：附加组件必须携带兼容性补丁，并在每次基线迁移时重新运行该检查。

### 为什么不做成默认

- 默认 bundle 必须在没有凭据时也能工作。该原型没有 GitHub 账户、clone 和模型就无法有效启动。
- 插件需要自己的 profile 和进程。桌面 profile 由应用拥有，不能被同时修改进程级环境的插件重启或重配。
- 默认开启的服务会在每次安装时消耗凭据、网络和后台算力。这是产品决策，不是打包细节。
- 仓库明确是研究代码。默认开启会让它的缺陷看起来像桌面缺陷。

## 备选方案

| 方案 | 交付内容 | 优点 | 成本与风险 |
| --- | --- | --- | --- |
| 仅文档 | 手动安装与兼容性修补说明 | 不增加包体、无默认风险、最快 | 使用者需自行构建并修改 profile；deb 不变 |
| 离线附加组件 | resources 中的构建产物，加设置动作和服务准备 | 无需 registry 访问；仍是可选；无默认界面 | 增加可选依赖和后台进程；需要卸载与升级处理 |
| 一等可选 bundle | Bundle 进入运行时包集和插件管理器可选列表 | 发现性和一键启用最好 | 需要上游式元数据、图标、语言和产品隔离例外；共处注意事项仍在 |
| 以补丁形式 vendoring | `patches/` 下的大补丁 | 仅靠本仓库即可复现 | 数百文件研究代码、上游漂移、审查与安全负担；不推荐 |

## 影响

- Linux 包增加可选界面，而不是默认功能。发布说明必须注明安装附加组件不会创建 GitHub 账户或启动服务。
- 附加组件必须把状态放在 deb 之外的用户 profile 下，不得把凭据写入包或仓库。
- 卸载和升级必须停止服务，按策略保留或删除状态，并不影响其他 profile。
- 针对固定基线的兼容性检查成为每次上游迁移的维护任务。
- 支持边界必须明确：上游拥有原型，移植版拥有打包与兼容性，操作者拥有账户、凭据与隔离。
- 附加组件不得绕过桌面的强制更新策略和单实例所有权。

## 实施计划

| 阶段 | 交付物 | 出口条件 |
| --- | --- | --- |
| 1 | 手动安装、两处 API 修补和服务要求的文档页 | 命令在固定基线和全新 profile 上可用 |
| 2 | 针对固定基线构建原型并运行测试的兼容性 job | API 漂移会让该 job 失败，而不是等发布后才发现 |
| 3 | 离线附加组件 tarball、设置安装动作和服务脚本 | 在干净的 Ubuntu 24.04 主机上完成安装、启动、状态、停止和卸载 |
| 4 | 视情况提升为一等 bundle | 上游提供元数据、语言、图标、隔离例外和责任人 |

每个阶段都需要自己的证据。原型构建成功不能证明 GitHub、飞书或模型凭据可用，面板截图同样不能。

## 风险

- 原型以桌面用户身份完整权限运行，可读取主目录。允许列表配置错误会把一条聊天消息变成代码变更。
- 对仓库有写权限的 agent GitHub 账户是供应链凭据，不能与人类账户共用。
- 后台执行和 GitHub 轮询可能在没有可见窗口时消耗额度和算力，与桌面本地优先的预期相悖。
- 原型的 API 面可能随任意 Harness 版本漂移；兼容性检查必须约束附加组件，而不是约束桌面发布。
- 独立 profile 会重复模型配置和存储，可能让期望单一 Desktop profile 的使用者困惑。

## 待决问题

- 附加组件应当创建 `superagent` profile 并写入其 patch，还是只打印命令？
- Linux 上以哪个服务管理器为准：systemd 用户单元、桌面自启动项，还是随附的 tmux 脚本？
- 面板是否需要桌面菜单项和窗口，还是在浏览器打开 loopback URL 就够？
- 更新策略的 Linux 标识是否是任何长期运行附加组件的前置条件，还是附加组件可以跟随桌面更新渠道？
